# ADR 007 — `api/` as a sub-package; Drizzle + `@vercel/postgres`; URL identity

## Context

[ADR 003](003-deploy-vercel-serverless.md) chose Vercel Postgres (Neon) + Drizzle
ORM for persistence and pre-authorized the dependencies (`drizzle-orm`, a
Postgres driver, `drizzle-kit`). It did not say **where those dependencies live**
or **how DB code stays out of the frontend bundle**.

The established pattern (M5, [retro 006](../retrospectives/006-research-endpoint.md))
keeps `api/` dependency-free: backend handlers import domain modules from
`app/src`, and *those* pull `zod` from `app/node_modules`. That trick works for a
shared, browser-safe library like Zod. It does **not** work for a Postgres
driver: DB access code must never be importable into the React SPA, and the
driver must never enter the frontend bundle.

M6 also needs a stable competitor identity. M5's `toCompetitor` used a
*provisional* name-slug id and its own comment deferred "real id/dedup" to M6.

## Decision

1. **`api/` becomes its own sub-package.** It gets an `api/package.json` with
   `drizzle-orm` + `@neondatabase/serverless` as dependencies and `drizzle-kit` +
   `@types/node` as dev dependencies, resolved from `api/node_modules`. Domain
   **types** are still imported transitively from `app/src` (one source of truth
   for the `Competitor` schema); only the DB-specific libraries live in `api/`.

2. **Driver: `@neondatabase/serverless`** (via `drizzle-orm/neon-http`).
   ADR 003 named `@vercel/postgres` first, but that package is now **deprecated** —
   Vercel Postgres migrated to Neon as a native integration and the transition
   guide points to Neon's own SDK. Since Neon is already the ADR 003 target, the
   Neon HTTP driver is the direct, non-deprecated equivalent: HTTP-based,
   single-shot queries, no pooled connection to manage in a stateless function.

3. **URL-based identity.** A persisted competitor's `id` is `websiteKey(url)`
   (normalized website), which is at once the DB primary key, the research dedup
   key, and the REST resource id. A pure `websiteKey` lives in `app/src/domain/`
   so the frontend and (transitively) the backend share one normalization.

4. **Repository seam.** All DB access is behind a `CompetitorRepo` interface; a
   drizzle impl runs in production and an in-memory impl backs node-only tests.
   The live Postgres path is deploy-verified, consistent with M5's live-model
   check.

## Consequences

- **Divergence from "dependency-free `api/`" — scoped, not abandoned.** Only
  DB libraries move into `api/`; the Zod-via-`app/src` transitive scheme is
  unchanged for domain types. The frontend bundle never sees the Postgres driver.
- **Tooling to wire:** `api/`'s `node_modules` must be installed on Vercel
  (add `npm install --prefix api` to the install command) and resolvable by
  vitest (root runner already imports `api/**`). Migrations are generated by
  `drizzle-kit` into `api/drizzle/` (committed) and applied at deploy/setup-time.
- **Identity change is a behavior change:** M5's research response `id` shifts
  from name-slug to URL key. Only the React `key` prop consumes `id`, so the UI
  is unaffected; one M5 test assertion updates.
- **`@neondatabase/serverless` binds us to a Neon endpoint** for both runtime
  and the seed/migrate scripts (they read `DATABASE_URL` / `POSTGRES_URL`).
  Acceptable — Neon is already the ADR 003 target, and this replaces the now-
  deprecated `@vercel/postgres` the ADR 003 had listed.
- Supersedes nothing; **extends ADR 003** with the structural specifics it left
  open. Written at M6, when the DB code first lands.
